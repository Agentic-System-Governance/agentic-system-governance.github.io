# 可审计性保障

[返回首页](../README.md)

**Auditability Assurance 的职责，是维持重建执行经过、追溯责任关系和评估合规情况的能力，使有权审查者能够核对发生了什么、谁依据什么权限参与，以及实际行为是否符合适用要求。** 记录的完整性、版本、保留期限与查阅权限支撑这些工作；保存日志本身还不足以回答审查问题。

以住宿报销任务为例。假设企业通常每晚最高报销 600 元，但允许有权负责人批准会议指定酒店的住宿例外。员工提交一晚 800 元的票据，随附“按本次会议指定住宿安排据实报销”的批准。报销 agent 根据批准及其关联材料核定 800 元，再委托支付 agent 付款。任务权限、例外审批程序和记录要求均已明确，审查要判断这次具体付款是否在批准范围内。

## 执行重建（Execution Reconstruction）

事后看到“已支付 800 元”，只能看到一个结果状态，尚不能知道报销 agent 当时依据什么核定。governance agent 应确保申请、票据、批准所指的会议安排、当时有效的报销规则和核定记录能够关联起来，再将付款委托、支付调用与到账结果接到同一申请上。

本例需要恢复当时的具体上下文：批准引用的是哪一版会议安排，该安排规定了哪家酒店及住宿日期，票据是否对应这些条件，报销 agent 交给支付 agent 的金额和用途是什么。若运行中只传递了“住宿已获批准”的摘要，审查仍需能够回到原批准及其引用材料，不能让摘要取代范围限定。

版本管理和业务日志可以保留这些关系，关键材料可采用受控引用，无需复制所有个人资料。今天打开的会议安排可能已经更新；一段事后生成的合理解释，也不能证明当时实际采用了什么依据。记录缺口应随执行经过一起呈现。

## 责任归属（Responsibility Attribution）

责任归属把具体行动连接到授权者、委托者、执行者和承担审核职责的主体。本例中，负责人批准住宿例外，报销 agent 判断票据是否符合该例外并核定金额，支付 agent 根据付款委托执行转账；governance agent 的核验与放行判断也需要单独留有依据。

审查应能从这笔交易回溯到付款委托，再到核定决定及适用批准。支付渠道显示的服务账号不能独自说明是哪次任务、哪个 agent 实例发起了付款，更不能证明负责人批准过每一项实际执行细节。委托记录应保留对象、金额、用途与权限范围，使执行时的责任分工可查。

这些记录说明各主体承担过什么职责、作过什么决定。某个 agent 发起付款，不足以认定它应对金额核定负责；负责人批准例外，也不等于免除了后续票据审核。责任关系的重建为进一步审查提供依据，不自动构成过错或法律责任裁定。

## 合规评估（Compliance Assessment）

对本例直接套用 600 元上限，会把有效例外误判为违规；只看到“已批准”，又可能忽略酒店、日期和费用用途的限制。审查应将实际付款对应到当时的规则、批准内容及其引用材料，判断例外是否覆盖这笔住宿费用，而不只是检查是否存在一条批准记录。

若保留的材料能够证明票据对应指定酒店与会议当晚、800 元属于获批住宿费用、批准人具备相应权限，且到账金额与核定一致，就可以支持这笔付款在所审查范围内合规。结论应指向这些证据和规则版本，不扩展为对所有报销过程的保证。

固定程序可核对金额、日期和身份；模型可辅助解释批准与会议安排的关联。剩余困难是把自然语言的批准范围落实到实际交易，并确认所用材料确为当时依据。若只留下“同意报销”而丢失其引用的安排，就应列明尚缺的范围证据，保留待确认结论。模型不能补造历史，存在日志也不能把未知自动变为合规或违规。
