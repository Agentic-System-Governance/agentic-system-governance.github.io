# 治理分析工作表

[返回首页](README.md)

选择一项具体任务，说明相应职责需要承担什么。写清主体、对象、条件与证据，比列出机制名称更重要。动机案例应直接进入对应职责页的“为什么需要”，本表用于分析，不另作案例讲解页。

## 任务与职责

| 问题 | 填写内容 |
|---|---|
| 任务是什么 | 目标、交付物、必须满足的条件、截止时间 |
| 分析哪项职责 | 明确本轮聚焦的治理功能，不一次展开全部问题 |
| 为什么需要 | 去掉该功能的具体失效路径、影响与其他职责补不上的原因 |
| 要求来自哪里 | 任务约定、组织规则、信息使用条件及有权修改者 |
| 可以做什么 | 主体、资料、工具、操作范围、资源预算与授权时效 |
| 谁负责 | 谁判断、谁执行、谁复核，哪些功能已经由现有程序承担 |

## 运行与证据

| 问题 | 填写内容 |
|---|---|
| 能看见什么 | 提议、调用、返回、外部状态、进展与不可见部分 |
| 失效发生在哪一步 | 一个具体执行过程中的错误、遗漏、停滞或未知 |
| 怎样响应 | 处理条件、时限、可执行动作与接管路径 |
| 处理权限是什么 | 重试、修正、变更、暂停或转交所需的现行权限 |
| 等待期间怎样安排 | 哪些可继续，哪些须暂停，谁仍负责 |
| 怎样确认结果 | 检查实际状态、影响范围、必要条件与未知部分 |
| 保存什么 | 要求、批准、动作、效果、异常、核验与责任关联 |
| 怎样保护记录 | 访问、保留、删除与敏感信息最小化条件 |

## 写入职责页前的检查

一个案例是否足以说明该职责？如果必须不断增加例外、角色和系统才能成立，先重新选择失效路径。

如果只写了“监测 agent”“人工确认”“记日志”或“自动恢复”，补充它具体观察、决定、改变或证明什么。使用成功提示时说明它支持的结论范围；声称职责必要时，也说明必要的功能已经由哪些安排承担。
