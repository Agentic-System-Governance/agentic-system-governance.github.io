# 治理目标的评估

[返回首页](README.md) · [共同难点](challenges.md)

## 评估什么

评估应回答治理系统是否履行了声明的职责，以及付出了什么代价。工作 agent 的最终成功率是相关结果，但不能单独说明授权、监督、恢复和追责有没有发挥作用。

系统至少需要说明任务、授权、故障范围、可见信息、可用控制手段和资源预算。观察不到的效果不能从评价中悄悄消失，应单独报告未知状态。

## 五项职责对应的检查

以下是这套职责设计建议使用的评价维度，不是对现有论文采用指标的汇总。

| 职责 | 可以怎样检查 | 需要同时报告 |
|---|---|---|
| 任务约定对齐 | 改变需求、系统能力与授权，检查协商后的交付条件和执行边界是否正确落实并持续有效 | 未决事项、语义遗漏、能力与权限对应、检查与控制覆盖、修订传播 |
| 执行监督 | 改变风险与可见证据，检查干预是否及时适当，实际效果是否支持继续或完成 | 检出率与误报率、干预时机和范围、合法进展、结果未知、错误完成声明 |
| 故障处置 | 检查失败解释的依据、对致因条件的修正，以及已受影响状态是否真正修复 | 归因证据与不确定性、恢复率与成本、修复覆盖、残留损害、新增影响、中止依据 |
| 多智能体协调 | 更新一个参与者的结果或安排，检查子任务归属、依赖与共同产物是否相应调整 | 无人跟进或重复工作、前提有效性、依赖覆盖、暂停范围、实际采用的版本 |
| 可审计性保障 | 让获准审查者重建执行、追溯授权和责任，并依据当时适用的要求复核实际行为 | 轨迹可重建范围、委托与审批关联、规则版本、合规结论依据、未决义务与证据缺口 |

## 怎样检验职责的必要性

各[职责页](README.md#按职责阅读)已用一个案例说明判断与行动。后续评价直接抽取相应要求与检查点，说明被移除的是哪些功能，以及交叉职责中的等价功能是否仍然存在；不应把五项职责假定为互不重叠的模块。

去掉一个名为“监测 agent”的模块，而保留所有功能等价的轮询与处理，不算去掉监督职责。执行监督包括风险监测、监督干预和结果核验；可以分别检查这些能力，但保留等价核验的系统不能视为移除了核验功能，仍能告警却无法制止行动的系统也不能视为保留了完整干预能力。比较需要说明真正移除了什么功能。

这些对照检验在所设条件下哪些功能有不可替代的作用，不是目前已经运行的实验，也不单独证明某种治理 agent 优于固定规则或人工安排。

## 任务恢复率怎样定义

可以先定义一个限定指标：在预先声明具有恢复路径的故障任务中，治理系统促成恢复且最终通过原验收条件的任务数，占该类故障任务总数的比例。

必须在运行前说明哪些故障被纳入、资源上限、允许的恢复方式、验收条件和观察窗口。不要事后剔除没有恢复的任务，再声称恢复率很高。

这个指标不能代表全部故障处置质量。任务重新取得进展之后，先前损坏的产物、污染的记忆或未确认的外部效果仍可能存在，需另行报告状态修复的覆盖范围。对于本来不可恢复的任务，应分别评估 获授权自主处理时自主中止的依据与结果，以及有人类介入时请求决定、等待和落实后续安排的情况；通过越权访问取得结果，也不能按“合规恢复成功”计数。

主稿现有指标表中的 Recovery R. 指受保护数据能否在后续被套取，属于信息泄露相关指标，不是这里的任务故障恢复率。二者应使用不同名称。

## 怎样区分治理带来的作用

在相同工作 agent、任务、工具与资源条件下，可以比较：工作 agent 按自身策略执行、使用固定的故障处理规则、由 governance agent 在限定权限内协调处理。固定规则也可能有效，不应只与完全没有恢复能力的执行者比较。

若治理方获得额外状态查询、更多预算或更强工具，应单独说明这些能力，并比较在相同能力下的其他安排。否则不能把全部收益归因于治理判断。

## 需要哪些情境

从各职责页唯一的动机案例提取正常与失效状态，保持原任务与权限条件不变。需要扩展时，优先改变同一案例中的观测、时限或执行结果，避免一次加入许多新规则，使比较对象失去清晰边界。

教学模拟器可以保留实际状态作为独立评价依据。被测治理方只能读取场景允许的信息，不能使用隐藏状态作决定；评价也不应直接把被测方自己的“允许”或“已完成”作为真值。

## 怎样报告结果

同时报告不当效果、合法任务完成、故障恢复、准确结束报告、人工负担与运行成本，并标明各比例的分母。发现时间需要说明从哪一个事件开始计时；观察窗口结束时仍未知的任务应单列。

后果指标应对应各职责页已经说明的失效点，分别报告不当行为、任务缺失、等待与证据可用性，不把不同后果压成一个看似统一的成功分数。

五项职责之间可以存在取舍。误报下降但漏报上升、恢复增加但成本失控，都需要呈现。采用更多检查不保证所有指标一起改善。
