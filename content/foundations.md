# 治理对象与职责边界

[返回首页](README.md)

## 为什么需要治理

用户通常交给 agent 一个目标，而不是一份写死每一步的操作清单。为了完成目标，agent 会选择信息、调用工具、修改计划，可能保存记忆或委托其他 agent。这些选择会使用权限、消耗资源，也可能影响任务以外的人。

一句“帮客户准备报价”没有自动说明底价能不能披露、折扣能承诺多少、邮件需不需要确认；一句“给订单退款”也没有解决超时后是否应重试、款项是否已经退回。这些是企业工作任务里的权限、执行与责任问题，不需要先引入一次安全事故。

**治理对象是被委托的任务、权力、行为及其后果，以及围绕它们的责任关系。** 模型、上下文、工具、记忆和协作网络，是这些要求需要具体落实的位置。

## 同时关注边界与履行

行为边界说明不能越过什么，例如不披露内部底价、不擅自增加采购预算。履行要求说明接受任务后应当做到什么，例如报表包含全部指定门店、客户交接覆盖全部目标记录。

二者不能互相替代。报表从未越权却漏掉一家门店，仍可能没有履行任务；报价成功成交却披露其他客户资料，也不能算正当完成。

治理还需要判断任务是否继续具备完成条件。如果获准的数据无法取得、预算已经耗尽，governance agent 应根据约定的决定权限决定调整或中止，或由人介入给出新决定，并说明未完成部分。

## 三种角色

| 角色 | 主要工作 | 在客服退款中的例子 |
|---|---|---|
| 工作 agent | 选择并执行完成任务的方法 | 核对订单、发起获准退款、查询结果 |
| governance agent | 在职责内作出治理判断，协调并监督处理 | 检查金额与收款路径、发现超时、控制重试并要求结果证据 |
| 人类或负责机构 | 授予和修订职责，承担相应管理与补救责任 | 制定退款权限、批准例外、接管无法自动处理的争议 |

治理系统包含上述相关主体、程序和技术控制。governance agent 是其中承担部分治理工作的 agent，不等于整个治理系统。固定的权限检查器也可以参与治理，但不会因为独立运行就自动成为 agent。

角色可以由同一系统兼任，但要能区分它依据什么作决定。工作 agent 的自检有价值；需要独立批准时，自检不能替代授权方的批准。

## 五项职责如何配合

五项职责按判断对象与承担的工作划分，可以共享证据、工具和执行机制。它们不是五个依次运行的阶段，也不要求每项都由独立 agent 承担。

| 职责 | 核心判断 | 需要落实的结果 |
|---|---|---|
| [Mandate Alignment](goals/01-mandate.md) | 系统承诺交付什么、允许怎样行动，如何将约定落实并保持有效 | 经交互协商确认的交付条件与执行边界，以及对应检查、控制和复核责任 |
| [Execution Oversight](goals/02-oversight.md) | 当前风险是否允许继续行动，实际效果是否支持继续或完成 | 风险判断、适当的放行或干预，以及有证据支持的结果核验 |
| [Fault Resolution](goals/03-troubleshooting.md) | 执行为何失败或偏离要求，怎样修正致因并修复既有损害 | 有依据的失败归因、运行修正及受影响状态的修复；保留未解决事项 |
| [Multi-Agent Coordination](goals/04-coordination.md) | 谁负责待办工作，前提是否满足，各方采用的状态与产出是否相容 | 子任务与跟进责任分配、依赖管理和一致性维护 |
| [Auditability Assurance](goals/05-accountability.md) | 实际发生了什么，依据谁的授权，行为是否符合当时适用的要求 | 可复查的执行重建、责任归属和合规评估，以及明确的证据缺口 |

Mandate Alignment 建立并维护交付条件和执行边界；Execution Oversight 监测风险、决定如何干预，并核验实际效果。发现执行失败或不符合要求时，Fault Resolution 调查原因、修正运行方法并修复受影响状态，无须先把常规重试耗尽。涉及多个 agent 和人类参与者的分工、依赖或状态相容性时，Multi-Agent Coordination 组织相关工作。Auditability Assurance 需要从运行时保留关联证据，使这些过程及其授权关系能够在审查中重建和评估。

交叉并不意味着重复检查。协调安排写作 agent 更新过期结论，执行监督核验更新后的报告是否满足交付条件；同一次检查可以提供双方所需的证据。故障处置修复产物及其依赖，结果核验检查实际修复范围。审计中的责任归属追溯参与者的授权与承担的职责；故障处置中的失败归因解释哪些条件促成失败，二者不能互相替代。五项职责的三个要点见[综述映射](survey-map.md)。

## 治理决定权限与接续决定

工作 agent 的自主执行与治理决定权限需要分别明确。工作 agent 能自动付款，不等于 governance agent 有权修改预算；governance agent 具有中止权限，也不意味着它必须自行执行每项业务操作。

获授权自主处理时，governance agent 根据有效任务约定和获授治理权限，自主处理状态变化、决定调整，并在判断无法继续时中止任务。权限覆盖的规则变更由它作出并更新任务约定，无需把所有困难都转成人工等待。

在有人类介入的设置下，可以由人修改规则或给出新决定。请求应明确事项和依据，等待期间保留任务状态、响应安排与跟进责任；受影响的行动暂停，其他获准工作可以继续。决定返回后，应将有效变更落实到相关执行者。

中止任务需要说明依据、已完成与未完成事项，以及已发生和待确认的外部效果。停止后续执行不等于撤销了在途动作。相关查询和后续处理仍应依据约定的权限，决定及其效果应留存以供事后追溯。

## 什么属于治理介入

工作 agent 发现网络错误后，按既定规则重试，是普通执行能力。治理系统规定哪些失败需要报告、监督重试是否超限、决定是否换用新工具，并核验后续结果，是对执行的治理。两者可以调用相同的重试机制，区别在于承担的职责与决定权。

governance agent 可以引导任务恢复，但不必掌握解决所有专业问题的能力。它可以安排重新规划或服务切换；获授权自主处理时自行作出获授权的调整与中止决定，在有人类介入的设置下请求相应决定。亲自重新编写报价或生成报表时，它又承担了工作角色。

## 工作失败与治理失败

一家门店查询持续失败，是执行故障。若治理系统按职责及时发现、尝试获准恢复、不把缺数当零值，并按约定的决定权限中止任务或请求新决定，说明部分结果与待处理事项，则治理仍可能履行了职责。未完成任务不必然意味着监督失效，关键还在于是否履行了被指派的发现、处理与交接责任。

反过来，即使任务偶然完成，也可能存在治理问题：越权读取的数据恰好有用，或者监督系统没有运行但这次没有出事。

判断治理失效，需要同时说明：它被指派了什么职责，具备或应具备哪些观测和控制手段，要求在什么条件与时间内处理，以及实际哪一步没有做到。不能要求一个只负责附件披露的检查器单独证明整个报价计算正确。

## 治理系统也需要约束

governance agent 应有明确的观测范围、干预权限、资源预算和升级路径。允许它暂停任务，不代表允许它修改用户目标；允许它核查资料，不代表可以无限收集个人信息。

原任务结束或取消后，针对在途请求的状态查询、审查与补救也需要明确权限。不能因为需要处理遗留影响，就默认所有原权限继续有效。

还应安排自身故障的处理：监测程序是否停止、处置是否一直无人执行、是否持续误拦截。可以由固定健康检查、独立复核和人工责任安排承担，无须无限增加监督 agent。任何保证最终都依赖声明清楚的可信组件和运行条件。
