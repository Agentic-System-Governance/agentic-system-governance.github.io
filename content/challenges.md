# 跨职责的共同难点

[返回首页](README.md) · [职责导航](README.md#按职责阅读)

五项职责各自可以有局部机制，难点还在于它们能否在同一次任务、跨多个工具与执行者持续配合。以下是这套职责设计需要处理的问题，不直接等同于已由文献确认的研究空白。

各职责页围绕一个任务说明问题定位、具体判断与职责边界。这里讨论这些职责在组合、交接与变化中持续发挥作用的共同困难，不另设案例系统。

## 任务要求难以完整表达

用户说的是目的，运行中出现的是参数、文件、消息和状态变化。治理要把二者连接起来，既避免把模糊目标解释得过宽，也避免把有效工作误判成违规。交付标准与权限存在冲突时，还要显露矛盾，而不是分别让局部检查通过。

这影响授权、监测和验收。可检验的问题是：同一要求换成另一种工具路径或参数表达时，判断是否仍然一致？

## 监督方不能看见全部事实

退款服务掌握处理状态，订单系统掌握订单进度，审批系统掌握批准范围。监督方不一定同时看得到；缺少回执也不能直接证明款项没有退回。

这影响故障判断、恢复选择和结束报告。可检验的问题是：当关键证据缺失时，系统能否说明未知、寻求信息，并避免把猜测当成确定结果？

## 治理决定必须赶上实际效果

提议时的授权可能在执行前变化；告警到达时，效果可能已经发生。权限检查、撤销和提交之间若没有明确的时间关系，就无法判断哪一次决定约束了哪一个动作。

这影响授权、干预和事后追溯。可检验的问题是：改变撤权与提交的先后顺序，系统能否保持声明的规则，而不是只在理想顺序下有效？

## 安全停止与任务推进需要共同考虑

禁止一切退款可以避免重复退款，却使正常客户无法得到处理；遇到超时一律重试又可能多付。治理应在当前事实、权限和服务能力内选择恢复，无法继续时，按约定的决定权限由 governance agent 中止任务，或由人介入给出新决定。

这影响处置、升级和验收。可检验的问题是：在相同任务与资源条件下，它减少了哪些不当效果，保留了多少正常工作，又解决了多少原本受阻的任务？

## 局部正确不保证整体合适

询价 agent 选定了报价，下单 agent 却不知道预算追加尚未批准；CRM 客户负责人更新成功，但指定旧共享权限仍在；最终报价没写底价，附件却包含底价表。局部检查通过，仍可能遗漏任务中的关键条件。

这影响多 agent 协调、故障传播和恢复核验。可检验的问题是：任务分支合并、结果转交和状态复用时，共享限制与证据要求是否仍在？

## 系统变化会让旧判断失效

换模型、更新工具、装入技能或复用新记忆，会改变实际行为。先前通过的监测与验收结果，不能自动覆盖新配置。一次恢复若修改了长期配置，还可能改变以后的任务。

这影响全部职责的持续有效性。可检验的问题是：能否识别哪些判断受更新影响，只对相关部分重新验证，并撤回失效状态及其必要的下游影响？

## 治理系统自身会出错

governance agent 可能误判、受不可信内容影响、失去响应，或没有真正可用的执行通道。工作 agent 也可能与监督方共享同类盲点。外置一个 agent 并不自动产生独立性、可靠性或制止能力。

这需要明确可信组件，检查监测健康，安排可用的控制通道与故障处理；有人类介入时还需明确人工接管条件。可检验的问题是：监督方失效或持续误拦截时，系统能否发现，并在声明的时间与故障范围内保持约定状态？

## 哪些适合继续形成研究问题

先把问题具体化：在什么任务、观测、权限、时间和故障条件下，需要保持什么性质？再比较最相关已有机制的保证与假设。如果现有机制在同等条件下已经满足要求，可以做集成与教学演示；若不能，才进一步界定缺少的保证。

“接口会失败”“日志不完整”“需要恢复”说明问题值得处理，尚不能单独证明新方法的必要性。[综述映射](survey-map.md)列出已有材料和进一步核查位置。
